# 本地摄影选片系统 · 设计

> 这份文档记录立项时的设计取舍与风险清单（为什么这么定，而不是怎么实现）。
> 实现细节以代码和 README 为准——功能清单里带 `[ ]` 的是当时的计划，未必是现状。

> 目标：把「几千张照片里挑出几十张」这件最耗人的事，从几小时压缩到几十分钟。
> 约束：完全本地运行，不联网、不上传、不注册账号。轻量级桌面应用，macOS + Windows 双平台。
> 假设的素材：尼康机身 · NEF 格式 · **每次拍摄同时出 RAW 和 JPG 两份** · 一次拍摄几千张 · 可能多台机身

---

## 一、三条不可动摇的设计原则

**1. 原片只读。**
系统对原始照片目录只做「读」。不移动、不重命名、不删除、不改写 EXIF。所有评分、旗标、色标、集合归属都写进独立的数据库文件；需要跨软件兼容时，另外导出 XMP sidecar。这条原则比任何功能都重要——选片工具出 bug 最多丢评分，不该丢照片。

**2. 键盘驱动。**
选片是重复性极高的肌肉记忆操作。设计目标：从导入到导出，全程不碰鼠标。鼠标只用于「点开某张图看看」这种低频动作。

**3. 快到你感觉不到加载。**
选片的节奏感一旦被「转圈等待」打断，人就会烦躁、草率。缩略图、预览图必须做到瞬时呈现，这是体验的分水岭，也是技术上最需要投入的部分。

## 二、系统架构（六层）

```
原片目录（只读：NEF + JPG）
   ↓
索引层        格式识别 · NEF/JPG 配对 · EXIF · 快速指纹 · SQLite 增量索引
   ↓
缩略图缓存    160 / 512 / 1600 三级，每个配对只生成一份
   ↓
智能分析      清晰度 · 曝光过欠 · 连拍相似分组（按机身隔离）
   ↓
选片交互      配对聚合显示 · 网格 / 单张 / 对比视图 · 全键盘操作
   ↓
集合与导出    筛选成集 · 选择导出 RAW / JPG / 两者 · XMP 兼容
```

第 1 层和第 6 层是系统与外部世界的边界，中间四层是内部处理链。

## 三、核心功能清单

### 1. 索引层（Indexer）

- 递归扫描指定文件夹，识别各厂商 RAW、JPEG、HEIC、TIFF、PNG。
- **RAW + JPG 配对**：同目录下同名不同扩展名的文件，视为「同一次快门」的两份产物，在系统中合并为**一条逻辑照片**。这是本方案的头号前置功能，详见第七节。
- **增量扫描**：对比「文件大小 + 修改时间 + 前 1MB 内容指纹」，只处理新增和变动的文件。第二次扫描几千张的库应该在秒级完成。**不做全文件哈希**（原因见第七节）。
- EXIF 提取：拍摄时间、机身型号 + **机身序列号**（多机身的关键）、镜头、焦段、光圈、快门速度、ISO、曝光补偿、白平衡、GPS、方向。
- **感知哈希（pHash）**：用于找重复图和相似分组，在缩略图生成时顺带算出，几乎零额外成本。
- 写入 SQLite，开启 WAL 模式。

### 2. 缩略图缓存（Thumbnailer）

三级缓存，对应三种使用场景：

| 级别 | 尺寸 | 用途 | 单张体积 |
|---|---|---|---|
| micro | 160px | 网格视图缩略图墙 | ~15 KB |
| grid | 512px | 网格放大、快速浏览 | ~90 KB |
| preview | 1600px | 单张查看、大致构图判断 | ~500 KB |

- 缓存文件按哈希前两位分桶存放（如 `thumbs/a3/a3f9...jpg`），避免单目录塞进几万个文件导致文件系统变慢。
- **核心技巧**：直接提取 RAW 内嵌的 JPEG 预览来生成缩略图，比完整解码 RAW 快 10-30 倍，且色彩是相机原味（尼康的 Picture Control 会体现在内嵌 JPEG 里）。只有在需要 100% 查看对焦时才做完整解码。
- **配对后缩略图只生成一份**（优先用 JPG，解码最快）。所以 RAW+JPG 双格式**不会**让缓存体积翻倍。
- 并行生成，后台持续补齐，**可中断、可续做**（几千张一次跑不完很正常，关掉应用再打开应该从断点继续）。
- 缓存是纯派生数据，删除后可重建；提供「清空缓存」按钮和可配置的体积上限。

### 3. 智能分析层（Analyzer）

全部本地计算，CPU 可跑：

- **清晰度检测**：拉普拉斯方差 / Tenengrad 梯度。自动标出拍糊的照片，尤其是连拍里跑焦那几张。
- **曝光分析**：读直方图，统计过曝（高光溢出）和欠曝（暗部死黑）像素占比。
- **连拍相似分组**：`同一机身 + 拍摄时间邻近 + pHash 距离 + 内容向量相似度` 多条件聚类。这是选片系统最核心的省力功能——把同一场景的 12 张连拍归成一组，你只需要在一组里选 1-2 张。**必须按机身序列号隔离**，否则两台机身同时拍摄时会把不相干的照片并到一起。
- **语义标签**（可选，Phase 2）：CLIP 零样本分类，之后可以按「猫」「日落」「人像」「夜景」直接搜。
- **闭眼检测**（可选，Phase 2）：人脸关键点，专治合影里总有人眨眼。
- **美学评分**（可选，Phase 3）：NIMA 类模型给构图/色彩打分，仅作排序参考，不作为决策依据。

### 4. 选片交互层（UI）

三种视图：

- **网格视图**：缩略图墙，可调列数（3-10 列）。支持按拍摄时间、机身、镜头分组显示。**按配对聚合**——一次快门显示一张卡片，不是两张。
- **单张视图（Loupe）**：大图预览，`Z` 键一键切到 100% 看真实对焦。
- **对比视图**：2-4 张并排，专门用于连拍组内选优。这是区分「能用」和「好用」的关键功能。

评分动作（对齐 Lightroom / Capture One 的行业习惯，降低学习成本）：

- 星级：1-5 星
- 旗标：Pick（保留）/ Reject（淘汰）/ 未标记
- 色标：红、黄、绿、蓝、紫、无

评分**以配对为单位**：给一张卡片打分，NEF 和 JPG 两份记录同时写入，导出时无论选哪种格式，评分都是对的。

筛选与排序：

- 按星级、旗标、色标、机身、镜头、焦段区间、ISO 区间、拍摄日期、清晰度分数组合过滤
- **按配对完整性过滤**：只看「只有 RAW 没有 JPG」「只有 JPG 没有 RAW」的孤立文件——用来发现拷贝不完整
- 排序：拍摄时间（默认用校正后时间）、文件名、清晰度、ISO

**相似组视图**：把连拍组折叠成一张「组卡片」，展开后是叠放的小图；组内可以一键把最佳那张升为 Pick，其余批量 Reject。

### 5. 集合与导出层

- **集合（Collection）**：手动把照片拖进集合，或保存筛选条件为「智能集合」（比如「2026 年 9 月 · 5 星 · 尼康 Z8」）。
- **导出**：
  - **格式选择：仅 RAW / 仅 JPG / 两者都导**（交付客户通常要 JPG，后期修图要 RAW，备份要两个都要）
  - 拷贝（默认）/ 移动（需二次确认，红色警示）
  - 重命名模板，支持机身相关变量，见第七节
  - 格式转换：RAW → JPEG、指定长边（如 2048px）、质量参数
  - 可选加水印
  - 可选保留原目录结构
  - 导出日志：记录导出了哪些文件、去了哪里，可回溯

### 6. 安全与备份层

- 数据库自动备份（每次启动前保留最近 7 份）。
- 评分可导出为 XMP sidecar，Lightroom / Capture One / digiKam 都能读，避免数据被锁死在本系统里。
- 「删除」操作默认只从索引移除，或送入系统回收站——永不直接删文件。

## 四、选片工作流（四轮收敛）

```
第 1 轮 粗筛   连拍分组去废片      （处理量最大，靠机器的相似分组 + 键盘快扫）
第 2 轮 精选   1:1 查对焦，打星    （唯一需要真正「看图」的一轮）
第 3 轮 定稿   按星级确认          （筛选 5 星 → 微调 → 锁定）
第 4 轮 导出   成集合输出
```

关键洞察：**第 1 轮的操作量最大但判断最廉价**（糊了、明显重复、曝光报废），所以应该让机器先做分组和标记，人只做「整组保留 / 整组淘汰」的批量动作。第 2 轮才是真正消耗审美判断力的一轮，界面必须为它做好一切准备（大图秒开、100% 对焦、快捷键顺手）。

一次几千张的规模下，这个分层更重要：如果第 1 轮不能靠机器把量砍到 1/3，后面几轮会累到放弃。

## 六、桌面应用技术选型

**已确定方向**：轻量级桌面应用 · 数据全部本地 · SQLite · macOS + Windows 双平台。

### 结论：Tauri 2 + Rust 后端 + 原生 HTML/CSS/TS 前端

`Tauri 2` 是「轻量级跨平台桌面应用」这个需求下最贴合的方案。外壳用系统自带的 WebView（macOS 上是 WKWebView，Windows 上是 WebView2），**不打包 Chromium**；后端是原生 Rust 二进制。

**体积与资源占用对比**（中等复杂度图像应用的粗略量级）：

| | Tauri 2 | Electron | PySide6 |
|---|---|---|---|
| 安装包 | 6-15 MB | 120-200 MB | 90-150 MB |
| 空载内存 | 60-120 MB | 200-350 MB | 120-200 MB |
| 冷启动 | < 1 s | 2-4 s | 1-2 s |
| 运行时依赖 | 系统 WebView | 无（自带） | 无（已打包） |
| 跨平台构建 | 各平台分别构建 | 可在 mac 上打 Windows 包 | 各平台分别构建 |
| 开发速度 | 中 | 快 | 中 |

**为什么选 Tauri**：

1. **体积和内存真的小**。对一个要处理几万张照片的应用，省下 300MB 常驻内存是实打实的体验差异。
2. **天然的安全边界**。前端（WebView）默认**无法访问文件系统**，所有文件读写必须经过 Rust 侧显式暴露的命令。这正好从架构上落实「原片只读」——不是靠自觉，是靠机制。前端就算有 bug 也碰不到你的照片。
3. **SQLite 零依赖**。Rust 侧用 `rusqlite`（静态链接 SQLite 本体），用户不需要额外装任何东西，整个数据库就是一个 `.db` 文件。
4. **单文件可执行**。Rust 编译产物是原生二进制，不需要 Python 解释器，也不需要 Node 运行时。

**要付的代价（说清楚）**：

- **需要装 Rust 工具链**（`rustup`，一次性，约 10 分钟，占用 ~1.5GB）。
- **编译比解释型语言慢**。首次全量编译 2-5 分钟；之后改 Rust 代码的增量编译 10-30 秒。**改前端（HTML/TS）是热重载，秒级生效**，不受影响。
- **打 Windows 安装包需要 Windows 环境**。这不是 Tauri 特有的问题，Electron 和 PySide6 也一样。标准做法是配一套 GitHub Actions，打 tag 时自动产出 macOS 和 Windows 两个安装包。

**开发环境**：Xcode 命令行工具、Node（≥ 20.12）、Rust 工具链，装齐即可开发。

### 前端：Vite + TypeScript，不用框架

- 这个应用的 UI 复杂度集中在两处：**网格的虚拟滚动** 和 **键盘交互**。这两件事用框架反而更别扭（React 的虚拟 DOM 与高频滚动更新天然冲突）。
- 用 TypeScript 是因为状态会变复杂（筛选条件、多选集、撤销栈），有类型能省大量调试时间。
- 不用框架意味着没有组件生命周期要对抗，渲染节奏完全由我们控制——这对稳定 60fps 是好事。

### 关键技术选型清单

| 用途 | 选择 |
|---|---|
| 应用外壳 | Tauri 2 |
| 后端语言 | Rust |
| 前端 | Vite + TypeScript（无框架） |
| 数据库 | SQLite（rusqlite，静态链接） |
| EXIF / MakerNotes | `kamadak-exif` + `rawler` 的元数据解析 |
| 图像解码 / 缩放 | `image` crate + libjpeg-turbo 缩放解码 |
| NEF 处理 | 四级降级策略，见第七节 |
| 哈希 | `blake3`（快速指纹 / 按需内容哈希）+ `image_hasher`（pHash） |
| 并行 | `rayon`（数据并行）+ `tokio`（异步任务） |
| 跨平台打包 | Tauri CLI + GitHub Actions |

### 桌面应用专属设计

**数据存放位置**（遵循各平台规范，不污染用户目录）：

| 平台 | 数据库 | 缩略图缓存 |
|---|---|---|
| macOS | `~/Library/Application Support/SP/library.db` | 同目录下 `thumbs/` |
| Windows | `%APPDATA%\SP\library.db` | 同目录下 `thumbs\` |

照片原片**永远不进这个目录**——原片在哪就在哪，系统只记路径和指纹。

**跨平台需要注意的差异**：

- **路径处理**：Rust 侧统一用 `PathBuf`，绝不手拼字符串。Windows 的反斜杠、盘符、UNC 路径都要能正确处理。
- **文件名合法性**：Windows 不允许 `\ / : * ? " < > |`，导出重命名模板时要过滤。中文和 emoji 文件名两个平台都要测。
- **大小写敏感**：macOS 和 Windows 默认不敏感，但格式化成大小写敏感 APFS 的 mac 是敏感的。**配对键必须大小写不敏感**，否则 `.NEF` 和 `.nef` 会配不上。
- **HEIC 支持**：Windows 10 及以下原生不支持 HEIC 解码，需要走 libheif，或者明确只支持 Windows 11。
- **回收站**：删除操作要走各平台系统 API（macOS 的 `NSFileManager.trashItem`、Windows 的 `SHFileOperation`），Rust 侧用 `trash` crate 统一封装。**永不直接删文件**。

**其他桌面应用的标配**：

- 单实例运行（防止第二次双击又开一个进程，两个进程写同一个数据库）
- 深色模式跟随系统
- 窗口位置和大小记忆
- 「在文件管理器中显示」调系统原生行为
- 后台任务（缩略图生成、AI 分析）要有进度条和「暂停 / 继续」，绝不阻塞界面
- 自动更新（Tauri Updater，Phase 2 再加）

## 七、NEF · JPG+RAW 双格式 · 大素材量的应对

针对实际素材特征：**尼康机身、NEF 格式、每次拍摄同时出 RAW 和 JPG、一次几千张、可能多台机身**。

### 1. 头号功能：NEF / JPG 配对

**这个问题不解决，系统就没法用。** 每次快门产生两个文件（`DSC_0001.NEF` + `DSC_0001.JPG`），如果按文件平铺，几千次快门会变成上万张卡片，每次选片你都要对同一张照片做两遍判断。所以配对必须在索引阶段完成，是 Phase 0 的第一优先级。

**配对规则**：同目录 + 主文件名相同（大小写不敏感）+ 扩展名分属 RAW 组和图片组 → 视为一次快门。

**设计要点**：

- **索引层每个文件一行，但增加 `pair_key` 字段**。这样天然兼容「某次只拍了 JPG」「某次只拍了 RAW」的混合情况，不需要特例。
- **界面按 `pair_key` 聚合**：一张卡片 = 一次快门。卡片角标显示这一对的状态：
  - `NEF+JPG` — 完整
  - `仅 NEF` — 缺 JPG
  - `仅 JPG` — 缺 RAW
- **计数以配对为单位**。你按了 3000 次快门，界面就说 3000 张——符合直觉。
- **评分广播**：给一张卡片打分，Rust 侧在一个事务里把该 `pair_key` 下所有成员写入相同评分。这样「评分与照片分离、可重建索引」的设计完全不受影响。
- **孤立文件筛选**：专门筛选「只有 NEF 没有 JPG」或反之。这个功能非常实用——**从存储卡拷贝到硬盘时漏了文件，靠它一眼就能发现**。
- **缩略图只生成一份**（优先用 JPG，解码最快，且色彩与 NEF 内嵌预览一致）。所以双格式**不会**让缓存体积翻倍。
- **1:1 对焦检查用哪个？** 用 NEF 内嵌的全尺寸 JPEG。尼康 NEF 通常内嵌一张全尺寸预览，质量足够判断对焦；若某机型没有，再降级到系统解码。

**配对键的构造**：`规范化目录（小写）+ 主文件名（小写）`。注意跨平台大小写差异——`.NEF` 和 `.nef` 必须能配上。

### 2. NEF 解码：四级降级策略

不要指望用一个解码库覆盖所有情况。设计成逐级降级的管线，每张照片记录实际走通了哪一级（便于事后诊断）：

| 级别 | 方案 | 说明 |
|---|---|---|
| 一级 | `rawler`（纯 Rust） | 快路径。纯 Rust 无 C 依赖，交叉编译到 Windows 不用折腾工具链 |
| 二级 | 系统原生解码 | macOS：Core Image / ImageIO<br>Windows：WIC + 尼康 RAW 编解码包。新机型往往系统支持得比开源库更快 |
| 三级 | **内嵌 JPEG 直抠** | 扫描 SOI/EOI 标记，取「最大且宽高合法」的那段 JPEG |
| 四级 | 占位图 | 仍索引元数据与文件，缩略图给占位图，不阻断流程 |

**关键认知：选片只需要「内嵌 JPEG 预览 + 元数据」，不需要完整 demosaic。**
相机拍完 NEF 时，已经在文件里存了一张全尺寸 JPEG 预览。直接取它，比任何解码库都快，而且色彩就是尼康 Picture Control 的效果——所见即所得，这对选片恰恰是优点。

**为什么第三级对你特别重要**：尼康 Z8 / Z9 引入了 **HE 和 HE\* 高效压缩**（基于 Tico 编码），第三方库的支持往往滞后一两年。遇到这类 NEF，一级和二级都可能失败——但**内嵌 JPEG 直抠永远有效**，因为它是从文件结构里直接抠图，不依赖任何库的格式支持。这条兜底让「新机型拍了但看不了」这种事不会发生。

三级实现要防的坑：NEF 数据段里可能出现假的 JPEG 标记。用「取最大的一段 + 校验宽高是否合理」可以规避。

**尼康 NEF 的结构要点**：
- NEF 是 TIFF/EP 容器。内嵌预览通常在 IFD1 或 Nikon MakerNote 的 PreviewIFD 中，可能有多个尺寸（小缩略图 160×120、中等预览、全尺寸预览）
- 压缩类型分：未压缩 / 无损压缩 / 压缩（有损）/ HE / HE\*。不同压缩类型不影响配对，只影响能否 demosaic
- Nikon MakerNote 里有 ShutterCount（快门数）等有用信息，可以显示出来供你判断机身使用强度
- **尼康 JPG 也带完整 EXIF，包括机身序列号**。所以配对的两边都有时间戳，可以交叉验证配对是否正确，也可以用来检测机身时钟偏移

**每张照片都要记录 `camera_serial`**——多机身场景下，分组、去重、时间校正全都依赖它。

### 3. 几千张的性能预算（RAW + JPG 双格式，按 8 核估）

一次快门 = 2 个文件。所以「3000 张」实际是 3000 NEF + 3000 JPG = 6000 个文件。但工作量并不翻倍，原因见下：

| 阶段 | 3000 次快门（6000 文件） | 说明 |
|---|---|---|
| 扫描 + 建索引 | 2-3 分钟 | 并行 EXIF 解析。JPG 解析很便宜，所以只是略多于纯 RAW |
| micro + grid 缩略图 | 2-4 分钟 | **只为一对生成一份**，用 JPG 解码，工作量不翻倍 |
| preview 1600 图 | 浏览时懒生成 | 预取相邻 3 张 |
| 配对计算 | < 1 秒 | 按 pair_key 分组，O(n) |
| 相似分组 | < 5 秒 | 按时间窗口聚类 |
| **合计首次导入** | **约 4-7 分钟** | 全程有进度条，可中断，可边导边看 |

**关键优化：配对后缩略图只生成一份**，所以缓存体积也不会翻倍。

资源占用：

| 项 | 3000 次快门 | 1 万次快门 | 10 万次快门 |
|---|---|---|---|
| `library.db` | 8-20 MB | 30-60 MB | 200-500 MB |
| 缩略图缓存 | ≈ 1.8 GB | ≈ 6 GB | ≈ 60 GB |

**重要：文件指纹绝不能用全文件哈希。**
一张 NEF 约 30-50MB，一次拍摄 3000 张就是 100GB+ 的读取量，磁盘会被拖死，首次导入从分钟级变成小时级。改用 **「文件大小 + 修改时间 + 前 1MB 内容哈希」** 作为指纹，速度快 50-100 倍，对个人素材库而言碰撞概率可忽略。真正的全文件 `blake3` 只在「查找完全重复的照片」这个后台任务里按需计算。

**缓存上限必须可配。** 10 万次快门的缓存会到 60GB 量级。默认上限 20GB + LRU 淘汰 + 「清空缓存」按钮。缓存是纯派生数据，删了能重建，要让用户放心删。

### 4. 多机身带来的四个真实坑

**① 机身时钟不同步 —— 最隐蔽，也最影响结果**
两台机身的内部时钟差几分钟，按拍摄时间排序就会交错混乱；而连拍相似分组**完全依赖时间邻近性**，时钟一乱，分组就废了。

必须提供「机身时间偏移校正」：在数据库里为每个机身序列号存一个偏移量（比如 -3 分钟），照片同时保留 `taken_at`（原始 EXIF）和 `taken_at_corrected`（校正后），**所有排序和分组统一用校正后的值**。

怎么发现偏移？最实用的做法：找两张「明显是同一瞬间」的照片（比如两台机身对着同一场景），系统算出差值并建议偏移量。Phase 1 再做自动推断。

**② 文件名冲突**
尼康机身默认是 `DSC_0001.NEF` 这样的连续编号，**两台尼康很容易撞名**（尤其换了存储卡后编号重置）。拷贝到同一目录会互相覆盖。
**导入、去重、导出一律以「文件指纹 + 机身序列号」为身份，绝不用文件名做主键。** 导出一律重命名，不沿用原名。

**③ 竖拍方向**
尼康通常把方向写在标准 EXIF 的 Orientation 字段，但不同机型、不同固件可能有差异。多机身混用时要确保「竖拍照片在网格里正确竖着显示」——**每台机身都要各自实测一遍**，这是体力活，但一旦出错会非常刺眼。

**④ 色彩风格不一致**
不同机身、不同 Picture Control 设置下，内嵌 JPEG 的色彩差异明显。因为我们直接用内嵌 JPEG，所以天然保留各机身的原味，这是好事。但要注意：如果后续做 AI 美学评分，模型对色彩风格的偏好可能造成不公平——**美学评分只作排序参考，不作筛选依据**，原因就在这。

### 5. 导出重命名模板要支持机身变量

```
{日期}_{机身}_{镜头}_{序号}
→ 20260916_Z8_2470_001.NEF
```

可用变量：`{日期}` `{时间}` `{机身型号}` `{机身序列号}` `{镜头}` `{ISO}` `{序号}` `{原文件名}`

- **格式选择**：仅 RAW / 仅 JPG / 两者都导。选 RAW+JPG 时，配对的两个文件套用同一个序号，保持成对
- Windows 侧必须过滤 `\ / : * ? " < > |` 和控制字符
- 序号位数可配（补零到 3-5 位）
- 重命名后若目标已存在，自动追加后缀而不是覆盖

### 6. 大素材量对界面的额外要求

- 网格必须**真虚拟化**：DOM 节点数恒定，只渲染可视区 + 上下各一屏。三千张和三十万张的滚动性能应该一样。
- 键盘快速扫图时缩略图必须**命中磁盘缓存**，所以导入完成后要有「预生成邻接预览」的后台任务。
- 提供**时间线侧边栏**：按日期 / 时段分段跳转，否则几千张里定位到某个场景要靠一直按方向键。
- **配对状态要一眼可见**：卡片角标显示 `NEF+JPG` / `仅 NEF` / `仅 JPG`，并能按此筛选。
- 导入与浏览必须能**并发**：导入到第 200 张时就应该能开始看前面那 200 张，不要等全部导完。

## 八、数据模型（SQLite）

```sql
-- 照片主表（每个文件一行；配对通过 pair_key 聚合）
photos (
  id INTEGER PRIMARY KEY,
  path TEXT UNIQUE,             -- 绝对路径（规范化后）
  fingerprint TEXT,             -- 快速指纹：size + mtime + 前1MB哈希
  content_hash TEXT,            -- 全文件 blake3，按需计算，仅用于查重复
  phash TEXT,                   -- 感知哈希，相似检测
  pair_key TEXT,                -- 配对键：规范化目录 + 主文件名（均小写）
  file_kind TEXT,               -- raw / jpeg / heic / tiff / png
  is_primary INTEGER,           -- 该配对中的主文件（RAW 优先），缩略图/1:1 取自它
  decode_path TEXT,             -- 实际走通的解码级别：rawler/system/embedded/placeholder
  nef_compression TEXT,         -- 未压缩 / 无损 / 有损 / HE / HE*
  file_size INTEGER,
  mtime INTEGER,
  width INTEGER, height INTEGER,
  taken_at INTEGER,             -- 原始 EXIF 拍摄时间（epoch）
  taken_at_corrected INTEGER,   -- 应用机身时间偏移后的时间（排序/分组用这个）
  camera_model TEXT,
  camera_serial TEXT,           -- 多机身的关键：区分是哪台机身
  lens TEXT,
  focal_len REAL, aperture REAL,
  shutter TEXT, iso INTEGER,
  shutter_count INTEGER,        -- 尼康 MakerNote 里的快门数
  orientation INTEGER,
  gps_lat REAL, gps_lon REAL,
  indexed_at INTEGER
)
CREATE INDEX idx_photos_pair ON photos(pair_key);
CREATE INDEX idx_photos_time ON photos(taken_at_corrected);

-- 机身登记表（时间偏移校正）
camera_bodies (
  serial TEXT PRIMARY KEY,
  model TEXT,
  time_offset_seconds INTEGER DEFAULT 0,   -- 时钟校正偏移，可为负
  first_seen_at INTEGER,
  note TEXT
)

-- 评分（与照片分离，便于重建索引时不丢评分）
-- 打分时按 pair_key 广播：一次快门的两份记录写入相同评分
ratings (
  photo_id INTEGER PRIMARY KEY,
  pair_key TEXT,                -- 冗余字段，便于按配对查询与聚合
  stars INTEGER DEFAULT 0,      -- 0-5
  flag TEXT,                    -- pick / reject / null
  color_label TEXT,             -- red/yellow/green/blue/purple
  updated_at INTEGER
)
CREATE INDEX idx_ratings_pair ON ratings(pair_key);

-- 分析结果（按配对记录，因为分析基于缩略图，一个配对只有一份）
analysis (
  pair_key TEXT PRIMARY KEY,
  sharpness REAL,               -- 清晰度分数
  overexposed_ratio REAL,       -- 过曝像素占比
  underexposed_ratio REAL,
  aesthetic_score REAL,
  has_closed_eyes INTEGER,
  face_count INTEGER
)

-- 相似分组
groups (id INTEGER PRIMARY KEY, camera_serial TEXT, created_at INTEGER, cover_pair_key TEXT)
group_members (group_id INTEGER, pair_key TEXT, similarity REAL)

-- 集合
collections (id INTEGER PRIMARY KEY, name TEXT, type TEXT, filter_json TEXT, created_at INTEGER)
collection_pairs (collection_id INTEGER, pair_key TEXT, added_at INTEGER)

-- 标签
tags (id INTEGER PRIMARY KEY, name TEXT)
pair_tags (pair_key TEXT, tag_id INTEGER, source TEXT)  -- source: manual / auto
```

**三个关键设计**：

1. **`photos` 每文件一行 + `pair_key` 聚合**。这比「一个配对一行、两个路径字段」更灵活——天然支持「只拍了 JPG」「只拍了 RAW」的混合情况，不需要特例代码。配对逻辑只存在于查询和界面层。
2. **`ratings` 与 `photos` 分表**。即使照片换了盘、挪了目录、重建了索引，你辛苦打的分也不会丢——重建时用 `fingerprint` 重新关联即可。
3. **`camera_bodies` 独立成表**。机身时间偏移是「一次性配置、长期生效」的数据，换素材、重建索引都不该丢。所有照片的 `taken_at_corrected` 由 `taken_at + 该机身的 offset` 派生。

**注意 `analysis` 和集合/标签都以 `pair_key` 为主键**——因为对用户而言「一次快门」才是最小单位，分析和归类都该按这个单位走。

## 九、性能设计（决定成败的部分）

| 场景 | 目标 | 手段 |
|---|---|---|
| 首次扫描 3000 次快门（6000 文件） | < 3 分钟 | 并行 EXIF 解析 + 快速指纹（不做全文件哈希） |
| 增量扫描 | < 3 秒 | fingerprint 对比，跳过未变动文件 |
| 单张缩略图生成 | < 150 ms | 解码内嵌 JPEG / JPG 副本，不做 demosaic |
| 3000 次快门 micro + grid | < 4 分钟 | 配对后只生成一份 + 并行 + 可中断续做 |
| 配对计算 | < 1 秒 | 按 pair_key 分组，O(n) |
| 网格滚动 | 稳定 60 fps | 真虚拟化，DOM 节点数恒定 |
| 大图切换 | < 100 ms | 预取相邻 3 张 preview |
| 相似分组（3000 次快门） | < 5 秒 | 按时间窗口聚类，O(n log n) |

其他要点：

- SQLite 开 WAL 模式，批量写入用事务包裹（单条提交会让索引慢 100 倍）。
- 缩略图缓存加 LRU 淘汰，上限可配（默认 20GB）。
- 前端图片解码放 Web Worker，避免主线程卡顿。
- 导入是**可中断、可续做**的后台任务，不是一次性阻塞流程。

## 十二、风险与注意事项

| 风险 | 应对 |
|---|---|
| **配对没做好，网格里每张照片出现两次** | 配对是 Phase 0 前置项；`photos` 加 `pair_key`，界面按 pair 聚合，评分广播 |
| **尼康 HE / HE\* 压缩的 NEF 第三方库不认** | 四级降级，第三级「内嵌 JPEG 直抠」不依赖任何库的格式支持 |
| RAW 解码慢，界面卡顿 | 一律走内嵌 JPEG / JPG 副本，完整解码只在需要时触发且不阻塞界面 |
| 多机身时钟不同步，排序和分组错乱 | `camera_bodies` 表存偏移量，排序分组统一用 `taken_at_corrected` |
| 两台尼康文件名撞名、互相覆盖 | 以「指纹 + 机身序列号」为身份，导出一律重命名 |
| **存储卡拷贝不完整，事后才发现缺文件** | 孤立文件筛选（只有 NEF 没有 JPG 或反之），一眼看出漏拷 |
| 全文件哈希拖垮首次导入 | 只用「size + mtime + 前 1MB」快速指纹；全哈希仅按需后台算 |
| 缩略图缓存吃满磁盘 | 上限可配（默认 20GB）+ LRU + 一键清空；缓存可重建 |
