# <img src="branding/icon-final.png" width="52" valign="middle" alt="S·P logo" /> S·P 选片

> **S·P —— Select Photo。Shoot thousands. Keep the best.**
> 千张过手，好片留下。

![CI](https://github.com/Joker-desire/SP/actions/workflows/ci.yml/badge.svg)
![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)

本地摄影选片工具。轻量级桌面应用，数据全部留在本机，不联网、不上传、不注册账号。

- 目标：把「几千张照片里挑出几十张」从几小时压缩到几十分钟
- 素材特征：尼康机身 · NEF 格式 · 每次拍摄同时出 RAW 和 JPG · 一次几千张
- 技术栈：Tauri 2 + Rust + SQLite，前端 Vite + TypeScript（无框架）
- 平台：macOS + Windows（Linux 未实测）
- 许可：MIT

设计取舍与风险清单见 [`docs/DESIGN.md`](docs/DESIGN.md)。

## 下载安装

到 [Releases](https://github.com/Joker-desire/SP/releases) 页面下载对应平台的安装包，双击安装即可，**不需要 Node、Rust 或任何运行环境**：

| 平台 | 文件 |
|---|---|
| macOS（Apple Silicon，M 系列） | `SP_<版本>_macos_apple-silicon.dmg` |
| macOS（Intel） | `SP_<版本>_macos_intel.dmg` |
| Windows | `SP_<版本>_windows_x64.msi`（或 `.exe`，二选一） |

装完之后：

- 数据（图库索引、选片标记、缩略图缓存）放在 macOS `~/Library/Application Support/SP/`、Windows `%APPDATA%\SP\`
- 删应用不会删照片——**原片全程只读**，重装后标记还在

### 从旧版本升级 / 应用内自动更新

> **v0.3.0 及更早版本请手动装一次 v0.4.0。** 旧版里没有内置更新器，收不到任何更新推送；这不是故障，也不用清数据——图库索引、选片标记、缩略图缓存都留在原来的数据目录里，装完自动接上。装好 v0.4.0 之后，往后就都能在应用内更新了。

启动约 8 秒后会静默检查一次；想手动查，点顶栏的**「关于 S·P」按钮**（ⓘ）打开关于窗口，里面有一枚「检查更新」。**没有新版本时会在关于窗口弹窗告诉你「已是最新版本」**，不用再盯着状态栏找提示；查到新版本时顶栏关于按钮右上角会亮一个小圆点，主窗口弹出面板，**逐条列出这一版的更新项**（来自 `release-notes/<tag>.md`，和 Release 页说明同一份），由你选「立即更新」还是「稍后」——**不会强制重启**，下载装好后才重启。检查超时或 GitHub 连不上时静默降级，不影响选片；**下载或安装失败会在面板里写明原因**（v0.4.3 起），Release 页面始终能手动下载。

更新走 Tauri 官方 updater：每个更新包都有 minisign 签名，公钥编译进 app，验签不过一律拒绝安装。签名私钥只放在仓库的 Actions Secrets 里（`TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`），**私钥丢了就再也推不了更新**，因此本地另有离线备份。发版时 CI 会额外产出 `latest.json` 与三个平台的签名更新包，见 `docs/AUTO_UPDATE.md`。

### macOS 第一次打开要先做一步

应用没有 Apple 开发者证书签名（$99/年，目前没买），只有 ad-hoc 签名。从浏览器下载的文件会带隔离属性，这时双击会提示**「应用已损坏，无法打开」**，而且**右键 → 打开也不管用**。

把 app 拖进「应用程序」之后，在终端执行这一行即可：

```bash
xattr -cr "/Applications/S·P.app"
```

隔离属性清掉后 Gatekeeper 不再拦截，之后双击正常启动，功能没有任何区别。

> Windows 同理会有 SmartScreen 提示，点「仍要运行」。

## 从源码跑

**双击 `run-dev.command`**，或在终端里：

```bash
./run-dev.command
```

首次运行会编译 Rust，大约 3-5 分钟；之后启动是秒级。改动 `src/` 下的前端文件会热重载，不用重启。

> 首次启动如果 macOS 提示来源不明，右键点 `run-dev.command` → 打开。

### 环境要求（仅开发时）

| 依赖 | 版本 | 说明 |
|---|---|---|
| Rust | stable | 装好后在 `~/.cargo/bin` |
| **Node.js** | **≥ 20.12** | Vite 用到 `node:util.styleText`，Node 18 及以下会直接报 `SyntaxError` |

`run-dev.command` 会自己扫描候选路径（Homebrew → nvm → `~/.local/node` → 系统），挑**版本最高且通过 `styleText` 检测**的那个，不信任 PATH 里的默认 `node`——很多人系统里装的是老版本 Node，直接用会启动失败。

常用命令：

```bash
npm run dev          # 只起前端（Vite），改界面用这个最快
npm run build        # 类型检查 + 前端构建
cd src-tauri && cargo test   # 后端测试
npm run bump 0.1.1   # 改版本号（三处一起改，见下）
```

## 发版：打 tag 即在 GitHub 出包

本地不再产出安装包——**推一个 `v*` 的 tag，GitHub Actions 会自动构建 macOS（两个架构）+ Windows 的安装包，并建好 Release**：

```bash
npm run bump 0.1.0                       # 同步改 package.json / Cargo.toml / tauri.conf.json
# 写 release-notes/v0.1.0.md：每行一条 "- xxx" 的简洁更新项，必做
git commit -am "v0.1.0"
git tag -a v0.1.0 -m "v0.1.0"            # 必须是 -a 附注 tag
git push && git push origin v0.1.0       # 等 Actions 跑完即可
```

版本号必须三处一致，否则打出来的包是 A 版本、关于窗口显示 B 版本——所以走 `npm run bump` 而不是手改。

**每次发版都要写更新项**：`release-notes/<tag>.md` 每行一条 `- xxx`，3–5 条、一句话一条即可。这份文件同时用于 Release 页说明和 `latest.json` 的 `notes`，客户端的更新面板会把它逐条列出来，用户点「立即更新」前就知道这一版改了什么。文件缺失、或里面没有 `- ` 条目，CI 会直接失败——以前写死的「更新说明见 Release 页面」等于什么都没说，现在不允许再发这种空说明。

> **两个踩过的坑**：① 必须 `git tag -a`（附注 tag）。轻量 tag 会被 `git push --follow-tags` 静默跳过——commit 上去了、Release 却没触发。② 撤 tag 时光删远程 ref 不够，已经触发的 Actions run 不会自动停，会照常构建并建出 Release，得再去 Actions 页面取消掉。

除了上面四个安装包，工作流还会为每个平台产出**带签名的更新包**和 `.sig`，等三个 job 全部完成后由 `updater-json` job 汇总生成 `latest.json` 一起上传——客户端的 `/releases/latest/download/latest.json` 就指向它。生成脚本 `scripts/build-updater-json.mjs` 会在任一平台缺签名时直接让 CI 失败，因为 Tauri 会先校验整份 JSON，缺一项会让**所有**客户端检查失败。

这两个仓库 Secrets 必须存在，否则打包照样成功、但产不出有效签名，自动更新会静默失效：

| Secret | 内容 |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | `npm run tauri signer generate` 生成的私钥全文 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 生成时设的密码 |

**私钥丢失是不可逆的**：公钥编译进了所有已安装的 app，丢了就只能让用户全部手动重装。本地离线备份和仓库 Secrets 都要留。细节见 `docs/AUTO_UPDATE.md`。

## 三条设计原则

**1. 原片只读。** 系统对照片目录只做「读」，不移动、不重命名、不删除、不改写 EXIF。评分全部写进独立数据库；需要跨软件兼容时另外导出 XMP。

这道约束不是靠代码自觉，而是架构保障：**前端 WebView 没有任何文件系统权限**，所有磁盘操作必须经过 `src-tauri` 里显式暴露的命令。前端就算有 bug 也碰不到照片。

**2. 键盘驱动。** 全程不碰鼠标。

**3. 零等待。** 缩略图缓存 + 分页加载 + 滚远自动释放位图，几千张滚动一样轻。

- **镜头筛选真正露出来**：数据链路（`library_facets` 的 `lenses`、后端 `p.lens` 条件）一直都在，但前端要求「至少两种有效镜头」才显示，只有一支镜头或 EXIF 读不到镜头时永远看不见这一栏。现在只要有照片就显示：标题带镜头数、可一键清除；超过 6 支先收起尾巴，点「显示全部」摊开，选中的镜头自动展开到可见

- **所有分面支持多选**：同一维里可以勾好几个值（两支镜头、好几天、几档 ISO…），**同维取并集、跨维取交集**；再点一次已选项＝取消，点「全部」＝清空这一维。前端筛选状态从标量改成 `Set`，后端 `PairFilter` 增复数数组字段并把 `build_where` 改成 OR 分组（旧单选字段保留给导出等场合，两边合并去重）；`__none__` 仍翻译成 `IS NULL`
- **侧栏顶部「已选条件」区**：每个选中的值一枚 chip，带维度名、点一下单独摘掉，旁边「全部清除」一键清空（顶栏「清除筛选」同效）。长镜头名折两行不被截断；选得多时列表内滚动并做底部渐隐
- 验证：`cargo test` 88 passed / 0 failed / 2 ignored、`cargo fmt --check`、`npm run build` 全过；另外单独验证了带签名密钥本地打包能产出 `.sig`、`latest.json` 生成脚本的三平台正常用例与「缺签名必须失败」反向用例、发版工作流 YAML 结构

- **修复：连续浏览时卡片报「预览提取失败」**（2026-11-06 本机复现）。同一张照片被多个线程同时请求缩略图时，写缓存用的临时文件名是固定的 `xxx.jpg.tmp`：后一个 `create` 会截断前一个正在写的文件，前一个 `rename` 移走之后，后一个再 `rename` 就拿到 ENOENT，整条请求失败。缓存目录里攒下 53 个 0 字节 `.tmp` 就是这么来的
  - 临时文件名改成「进程号 + 原子序号」唯一；`rename` 撞上别的线程已写好的同一份缓存视为成功
  - 0 字节缓存不再算命中（重新生成），进程首次生成缩略图时清理十分钟前的残留 `.tmp`
  - 读缓存拿到空文件就删掉重生成一次自愈；前端失败占位符改成「点此重试」，悬停可看具体原因
  - 补两个回归测试：同一照片 8 路并发生成、0 字节缓存重建

- **色标**：保留 / 星级之外的第三条轴。同一批照片里「要修的」「要发的」「给客户看的」常常重叠，星级一旦被拿去表示去留，就再也腾不出手表达批次——色标颜色本身不表意，你定它是什么意思
  - 键位：`6` `7` `8` `9` 是红黄绿蓝，**减号 `-` 是紫**（`0` 已经是清除星级、`1`-`5` 是星级，第五个色没有数字可用了，所以挂在它在键盘上的邻居身上）；再按一次同一个键＝取消该色标
  - 大图底栏有对应的五个色点，点第一次是标、点第二次取消；卡片左边一条竖色带，侧栏「色标」可按颜色筛（再点一次取消）
  - **和星级、去留完全独立**：标红色不动决策也不动星级，`⌘Z` 一步退掉整批，清色标不会误删你的评分
  - 老库升级不用做任何事：色标列会自动补上，以前的标记一个不少

- **修复：加了色标之后老库会打不开**（2026-09-24 本机跑出来的）。给 `decisions` 补列时把 `CREATE INDEX idx_decisions_color` 和 `CREATE TABLE` 写在了同一份 schema 脚本里：老库上建表是空操作（表已存在），索引却立刻要 `color` 这一列 → 整批脚本失败 → 库打不开 → 应用退化成内存库兜底，界面提示「本次运行不会保存任何索引」。**你的数据一个字节都没丢**，只是那一趟什么也存不下
  - 现在的顺序是固定的：**先看清这个库是不是我们的 → 建表 → 补新列 → 最后建索引**。补列在索引之前，索引引用的列才能保证已经存在
  - 单条索引失败不再拖垮启动（只打印提示）：索引只影响快慢，不该让整晚的选片结果挡在门外。原本靠「索引失败」报警的职责，交给新加的最小骨架列校验来承担

### v0.2.0（2026-09-24）

装过 v0.1.0 的直接覆盖安装，**选片标记和图库索引都不动**。这一版主要是「让机器先把明显废片挑出来」加上几处手感的补齐。

**为什么重点做它**：对焦点是最靠得住的判废依据之一——对在眼睛上和对在背景上是两张完全不同的照片，而这种事 EXIF 里没有任何通用字段会告诉你。加上已有的清晰度 / 曝光，机器能替你排掉两类硬伤。

- **对焦框**（大图里 `O` 键或底部「对焦点」按钮，**默认关**）：把相机按快门时真正用上的那一块画在大图上，缩放时框跟着图走。数据来自尼康 MakerNote 的 AFInfo2，是**传感器原始像素坐标**，精度能到画面百分之几；详情面板「曝光」小节同步显示位置与区域模式。读不到（非尼康 / 机身没写）就不画，不报错
  - 尼康以外的机身目前读不出来：这笔数据每家都藏在自家的 MakerNote 里且格式各异，手上没有别的机身可以反推布局

**手感**

- **重做 `⇧⌘Z`**：撤销之后还能再往前一步，有新的标记时清空重做栈
- **窗口大小位置记忆 + 单实例**：下次打开回到上次的位置；再启动一次会把已有的窗口提到前面，不再两个进程各持一个 SQLite 连接写同一个库（选片状态会打架，而这类问题排查起来极费劲）
- **`F` 全屏**看图（大图里复位缩放挪到 `⇧F`，`0` 被清除星级占了）
- **选片进度**：页脚显示「已过目 X / Y（Z%）· 保留 N」，打了星也算过目
- **批量标记**：操作栏「批量 ▾」对当前筛选出来的**全部**照片（含还没滚出来的那些）一次性标保留 / 淘汰 / 清除 / 打星，一次 `⌘Z` 整批退回

## 界面怎么用

界面的核心判断是：**照片是主角，其余一切都退到后面**。所以网格里除了图什么都不抢眼，只有「配对缺失」这种真需要你看一眼的信息才给彩色徽标。

（下面是一张示意图，路径与数字都只是示例。）

├───────────────┬──────────────────────────────────────────────┤
│ 文件类型       │ [搜索文件名…] [排序 ▾] [紧凑|标准|大图] 1,000 张 │

**选文件夹时会先问你要多大范围**：如果选的文件夹里还有子文件夹，会弹出一张勾选表——默认全选，也就是整目录递归；只想看这个文件夹自己的照片就**一个都不勾**（等于只读这一层、不进子文件夹）；只要某几个子目录就只勾它们。勾选结果会记住，之后点「重扫」沿用同一范围。文件夹里没有子文件夹时不弹表，直接扫。

**主区是分组视图**：照片按顶栏「分组依据」下拉选的维度收组（组名吸顶、可折叠），分组依据除了文件夹，左侧筛选栏的每一维都能当；文件夹分组显示相对路径，子文件夹自带母文件夹。点任意一张进单张大图（Loupe）看细节、按 `P`/`X` 标去留。

**按错了直接撤销**：`⌘Z` / `Ctrl+Z`（或顶栏「撤销」）一步步退回上一步标记，批量标记和连拍里一次改一组也是一次退干净。撤销后可以再标，两者互不干扰。

**顶栏「清空」**回到未选文件夹的状态：不删原片、不碰索引库，选片标记也原样留着，重扫同一个文件夹会自动回到照片上。接着选下一个文件夹就行。

**换文件夹不会串台**：旧文件夹的照片会留在库里（为了标记能复用），但界面只显示当前文件夹范围内的照片，导出和左侧计数同理。

**缩略图缓存会一直长大**，页脚右下角实时显示占用（缩略图 + 索引库合计）。放大查看过的照片还会多一份 4096px 的高清档，是这里增长最快的一项。点它、或点顶栏的「清理」，都能打开清理面板：只清缩略图最安全，索引和选片标记都不会动；需要腾更多空间时可以连索引一起清，选片标记仍然保留，重新扫描后会自动回到照片上。

**大图可以放大看细节**：滚轮缩放（以鼠标位置为锚点）、双击放大 / 再双击复位、放大后按住拖动平移。右上角控件条显示当前倍率，`1:1` 是一个图像素占一个屏幕像素——判断有没有对上焦就用它。放大超过 1 倍时才会去生成高清档，换上来之前先用 1600px 顶着，倍率和平移都不变，只是突然变清晰。翻页自动回到整图。

**筛选可以叠加，也可以多选**：不同维度之间取交集（「11 月 8 日 + 保留 + 180-600」），同一维度里可以勾好几个值、彼此取并集（「180-600 或 100-400」）。点一次选中，再点一次取消，点「全部」清空这一维；不用专门跑去找「全部」那一项。

**选中的条件都摆在侧栏最上面**：一枚 chip 对应一个值，点 chip 单独摘掉；旁边「全部清除」一次清空，工具栏的「清除筛选」也是同一个动作。选得太多时这块自己滚动，窄轨上的数字会告诉你一共还筛着几条。

**筛选栏的计数是整个图库的口径**，不是「在当前结果里再数一遍」。这样点开侧栏看到的数字始终稳定，不会因为叠加条件而缩水到看不懂。

**左侧筛选栏可以收起**：点顶上的「筛选」把手（或按 `\`）收成一条窄轨，把宽度全让给照片；窄轨上的小数字是正在生效的筛选条件数。每一栏的标题也能单独点开 / 收起，标题支持 `Enter` / 空格，状态重启后保留；某一栏里有筛选条件时会自动展开，不会出现「结果变少了却找不到在哪筛的」。

**镜头这一栏只要有照片就在**：标题显示当前图库有几支镜头，点某一支筛、再点一次取消，标题后的「清除」直接取消。镜头超过 6 支时先只露前 6 支，点「显示全部」摊开；读不到镜头型号的照片归到「未知镜头」，也能单独筛掉。

**拍摄日期按月份折叠**，默认只展开最近两个月——几百天全铺开会翻到崩溃。筛选到某个日期时，它所在的月份会自动展开。

**分页加载 + 视口外卸载位图**：滚到哪读到哪，滚远的卡片把解码后的位图还给系统（数据 URL 仍在内存缓存里，回来时秒恢复），几千张不会撑爆内存。主区恒为分组视图，看细节点进 Loupe。

**彩蛋默认关**：连点顶栏 logo 5 次开启（再连点 5 次关闭），只写 localStorage，不碰数据库 / 标记 / 导出。开启后有四样小东西：空状态显示一句摄影名言、一整批「未标记」归零时页脚轻弹一下、`⇧D` 切暗房安全灯、`↑↑↓↓←→←→BA` 给卡片套上胶片齿孔边框。暗房会给整屏蒙红，**仅用于夜间浏览，别拿它判断照片色彩**；它只在当前会话生效，重启自动恢复正常。另外「关于」窗口里按住 `⌥` 还藏着一句话。

## 自动化的部分

这一版把「需要点按钮的地方」尽量砍掉了：

| 动作 | 之前 | 现在 |
|---|---|---|
| 选文件夹 | 选完还要点「扫描建索引」 | 选完即扫，扫完直接出图 |
| 打开应用 | 每次都要重新选文件夹 | 自动恢复上次的图库，先铺图再增量重扫 |
| 新拷进来的照片 | 要手动点扫描 | 启动时自动增量扫描，发现新增；没变化则不重排界面（不闪） |
| 滚动 | 只显示最近 200 张 | 滚到底自动续载，直到取完 |
| 内存 | 每张卡片的位图一直挂着 | 滚出 2400px 就释放，滚回来秒恢复 |
| 扫描过程 | 要等全部扫完才一次性出图 | 边扫边铺：入库按批提交，已入库的先显示，过程中可以照常滚动与标记 |
| 换文件夹 | 上一个文件夹的照片还会混在网格里 | 视图随文件夹走；旧记录留着复用标记，但不再出现在界面上 |

时间线上这些是怎么串起来的：

```
启动 → 读 localStorage 里的文件夹
     → 先用已有索引把网格铺出来（不等扫描，秒开）
     → 后台增量重扫（文件没变的话是纯 stat，一两秒）
     → 有变化才重排界面
```

**「自动重扫」之所以敢在每次启动都做，靠的是增量扫描的快路径**：先比「文件大小 + 修改时间」，一样就跳过，连文件内容都不读。退化成读内容的话，几千张就是几个 GB 的读取，这个功能就不成立了。`indexer.rs` 里有一条测试专门守这个性质（把库里的指纹故意改错，验证扫描仍然走快路径）。

## NEF 为什么能显示：抠内嵌预览

RAW 是容器格式，浏览器内核天生解不了——**任何选片工具想显示 NEF，都必须自己想办法拿到像素**。常见做法是完整解码 RAW（demosaic），但那很慢。

这里走的是另一条路：**相机在写 NEF 的时候，已经顺手在文件里存了一张全尺寸 JPEG 预览**。把它抠出来直接用：

- 比完整解码快得多，也**完全不需要 demosaic**——选片只需要看图，不需要像素级正确
- 色彩是那台机身的原味（相机自己渲染的）
- 和相机型号无关，**任何 RAW 格式都吃得下**（CR3 / ARW / RAF / DNG 同理）

抠的算法在 `thumb.rs`，有一点很关键：**不能简单地找「SOI 之后的第一个 EOI」**。RAW 里的预览自己带 EXIF，而 EXIF (APP1) 里可能又嵌着一张小缩略图；按标记段正确解析才不会撞上那张小图的 EOI 截出残缺数据。这也是为什么测试里专门造了一个「嵌套缩略图」的样本。

抠出来的是一张全尺寸 JPEG 预览（多数机身五千到六千像素宽，体积几十到几百 KB），三级缩略图再由它依次缩出。

## 性能：为什么必须给依赖开优化

同一张 NEF，从「抠预览」到「三级缩略图落盘」这一步，debug 构建比 release 慢**一个数量级**（二十倍上下），而 `tauri dev` 跑的正是 debug。所以 `Cargo.toml` 里有：

```toml
[profile.dev.package."*"]
opt-level = 3
debug-assertions = false
overflow-checks = false
debug = false
```

只优化依赖、自己的代码保持快速增量编译。**开发时滚动一屏照片从「几分钟」变成「几秒」，代价只是第一次编译多等几分钟。**

另外两道防止内存被打爆的闸门：

- 前端只请求视口内的缩略图，并且排队限制 4 路并发
- Rust 侧还有一道 `Limiter`（`thumb::global_limiter`），因为一张四千多万像素的预览解码成 RGB8 就要一百多 MB，不能指望调用方自觉

**吞吐取决于素材本身**：瓶颈是「整张预览解码」，而这一步是能并行的——4 路并发下，几千张的图库可以边滚边补，不需要等全量生成完。

关键在于**按需生成**：你只为你真正看过的照片付解码成本，没翻到的永远不花时间。

想量自己素材的话，跑一次就能看到数字：

```bash
SP_SAMPLE_DIR=/path/to/shoot cargo test thumb_throughput -- --ignored --nocapture
```

> 一个容易误判的现象：如果窗口被别的窗口挡住（比如从终端启动后没切过去看），WebKit 会暂停渲染，缩略图几乎不加载——那是浏览器的省电策略，不是卡住了。把窗口切到前台就恢复正常。

**还能再快的地方**（暂未做）：目前是「整张解码 → 再缩放」，而解码一张全尺寸预览（五千万像素级别）就是整条链路的绝对大头。JPEG 支持按 1/2、1/4、1/8 直接解码（DCT 尺度变换），做 512px 网格图时只解 1/4 尺寸就够，足够再快好几倍。代价是要绕开 `image` crate 直接用 `zune-jpeg` 的 scale 选项。等素材量大到滚动跟不上了再做。

**约定**：所有跨进程调用都收在 `src/main.ts` 里，Rust 命令和前端调用一一对应，改接口时两边一起改。

| 导出 `lib` | 清单 CSV 内容与转义、重名加后缀、同大小跳过、**原片目录零改动** |
| 清理 `lib` | 只清缩略图不动数据库、清索引保留选片标记、全部清空才删标记、目录本身保留 |
| 解码与缓存 `thumb` | 四级解码路由（内嵌→位图→RAW→占位）、RAW demosaic 兜底、缓存 2GB 上限触发、LRU 按访问时间淘汰、水位线回弹 |
| 导出与连拍 `lib` | 文件范围（raw/jpeg/both）、命名模板占位符替换、连拍按时间聚类分档、组内替换、序号稳定 |

> 两条来自真实踩坑的教训：
>
> 1. 早期测试全走内存库（`open_in_memory`），`open()` 的文件路径分支从没被执行过——而它恰恰是启动时唯一会碰的地方。新增的文件库测试就是为了堵这个洞。
> 2. 筛选条件会拼成动态 SQL，类型系统管不着字符串。所以用真实的扫描链路造数据，把每个维度都过一遍——`%` 不转义会把整个图库匹配出来，`_` 不转义会让搜 `A_B` 连带把 `AXB` 找出来，这两条都有专门的测试。

另外有一个需要真实素材的抽查测试（默认跳过）：

```bash
SP_SAMPLE=/path/to/DSC_0001.NEF cargo test real_nef -- --ignored --nocapture
```

合成样本证明不了「真机能用」——不同机身的 NEF 布局、内嵌预览的尺寸都不一样，换机身时跑一次。它会打印抠出的预览尺寸和各级缩略图的耗时与体积。

## 启动失败时不会「没反应」

双击启动看不到终端输出，所以任何在启动阶段的硬退出，对用户来说都等于「点了没反应」。这里做了三层：

1. **能自愈的就自愈。** 上次在写入过程中被杀掉会留下「0 字节库 + 热 journal」，而 SQLite 的恢复流程本身要删掉那个 journal，删不掉就会一直失败——一旦这样，应用会永久启动不了。现在小于一页的文件（不可能是有效数据库）直接丢弃，附属文件一起清掉，原地重建。够一页的一律**改名隔离**（`library.db.bad-<时间戳>`）而不是删除，宁可多留个文件也不冒删错的风险。
2. **实在打不开就把应用撑起来。** 退回内存库，界面上给一条红色横幅，写清楚路径和原因。能看能操作，但明确告诉你「本次运行不会保存索引」。
3. **线索落盘。** 启动异常同时写进数据目录的 `startup-error.log`；下次启动成功时自动删掉，免得排查时看错现场。

## 几个关键技术决定

**文件指纹不做全文件哈希。** 一张 NEF 三四十 MB，几千张就是上百 GB 的读取量，会把首次导入从分钟级拖成小时级。改用「文件大小 + 修改时间 + 前 1MB 内容哈希」，快 50-100 倍。

**`photos` 每个文件一行，用 `pair_key` 聚合。** 而不是「一个配对一行、两个路径字段」—— 后者遇到「某次只拍了 JPG」就要写特例。现在配对逻辑只存在于查询和界面层。

**工作集按 `pair_key` 而非 `photo_id`。** 对用户来说「一次快门」才是最小单位，分析结果、集合、标签都按这个单位走。

**`decisions` 与 `photos` 分表。** 主键是 `pair_key`，照片换盘、挪目录、重建索引都不会丢标记。
